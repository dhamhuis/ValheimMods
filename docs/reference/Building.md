## API and behavior

`Player.RequirementMode` values in this fingerprint are `CanBuild = 0`, `IsKnown = 1`, and `CanAlmostBuild = 2`. The method body preserves station, DLC, and build-key checks before its resource loop. For `CanBuild`, it checks each resource with the player's `Inventory.CountItems(name, -1, true)` against `Piece.Requirement.m_amount`; other modes use different logic.

Targeted IL inspection established that `Player.UpdatePlacement` calls `HaveRequirements(piece, CanBuild)`, then `TryPlacePiece`, then `ConsumeResources(piece.m_resources, 0, -1, 1)` when placement succeeds and the piece's free-build key is not active. `ConsumeResources` filters requirements by the current station's `m_upgrader` and each requirement's `m_upgraderResource`, calculates `GetAmount(qualityLevel) * multiplier`, and calls the name-based inventory removal overload with world-level matching enabled. `GetAmount(0)` returns the base `m_amount` in this fingerprint.

### BuildFromStorage implementation

[BuildFromStorage](../../BuildFromStorage/README.md) scopes storage counts to the local player's `HaveRequirements` checks for `CanBuild`, including Hammer UI and placement checks. It adds counts only to the player's inventory query, leaving vanilla station, DLC, and free-build checks intact. Before placement, it plans the complete cost using player inventory first and nearby storage ordered by distance; it reserves only storage needed for that placement and consumes those portions after vanilla consumes the player inventory.

The mod reuses [`ContainerRegistry.IsAccessible`](../../ValheimMods.Common/src/ContainerRegistry.cs) and [`StorageRange`](../../ValheimMods.Common/src/StorageRange.cs). Its storage candidates must be accessible, within the configured player-centered radius, closed, and currently owned by the local client. This avoids starting an asynchronous ownership request in the synchronous placement flow. The configured radius defaults to 20 m and is clamped to 1–100 m.

### Shared Hammer/Cultivator engine - 2026-11-24

Targeted IL inspection established that `Humanoid.GetRightItem()` returns `m_rightItem`, and `Player.UpdatePlacement` reads this equipped item and the active `PieceTable`. The normal placement path calls `HaveRequirements(piece, CanBuild)`, then `TryPlacePiece`, then consumes `piece.m_resources`; this is not a Hammer-only cost API. `TryPlacePiece` refreshes the placement ghost/status, rejects invalid statuses with vanilla feedback, and calls `PlacePiece` on success. Neither its body nor the common cost path was replaced.

[`PlacementStorage`](../../ValheimMods.Common/src/Placement/PlacementStorage.cs) registers clients by equipped-item drop-prefab name: `Hammer` for BuildFromStorage and `Cultivator` for [FarmFromStorage](../../FarmFromStorage/README.md). This is the mod's tool-routing policy; prefab names and the live Cultivator menu/content must be confirmed in game. Other tools and remote players remain outside the storage scope. Requirements are read directly from the selected piece, so no crop/seed/sapling whitelist is introduced, and `IsKnown`/`CanAlmostBuild` discovery calls remain vanilla.

The first client installs and verifies one namespace-scoped Harmony patch set under `hoose.valheim.sharedplacementstorage`; the last client removes it. Radius/log callbacks belong to the selected client. The former BuildFromStorage allocation, reservation, inventory-first removal and storage-consumption logic now lives in this engine. Tests exercise both clients, distinct radii, exact consumption, failed placement, access/ownership filtering, container lifecycle and unloading in either order. They model resource-bearing pieces, not actual prefabs or live network transactions.

FarmFromStorage has a soft BuildFromStorage dependency to load after it when installed. Registration rejects the old `hoose.valheim.buildfromstorage` inventory-count patch owner explicitly, because that standalone implementation also scoped all placement tools and would compete with farming. Install the updated BuildFromStorage development DLL and identical current common DLLs; an old prepared ZIP is not this migration.

The user observed initially lit unavailable Cultivator icons that corrected after reopening. Production-linked stub tests model incremental refresh and verify inventory, storage and missing-resource indicators, reopening, remote players and Hammer routing. A later report of plants enabled and placeable without materials was traced on 2026-11-26 to seeds in nearby chests: with inventory and nearby storage emptied, all entries were greyed and placement was rejected, and adding Flax to a chest enabled and planted Flax. The user also confirmed on 2026-11-26, after a fresh game start, that the Cultivator icons were correct on the first menu open.

The `Player.HaveRequirements(Piece, Player.RequirementMode)`, `UpdatePlacement(bool, float)`, `TryPlacePiece(Piece)`, `ConsumeResources(Piece.Requirement[], int, int, int)` and `PlacementCostDisabled` signatures were also rechecked against this fingerprint. ### No-cost and plant health checks - 2026-11-25

Targeted method-body inspection of the same `9B7EEDA2705790B33BB66DD0F092D65EB24F73333B061648A186BD687F534CA4` game assembly shows that `Player.HaveRequirements(Piece, CanBuild)` returns true before its resource loop when the global key returned by `Piece.FreeBuildKey()` is active. `Player.UpdatePlacement` also skips the requirement check when `m_noPlacementCost` is set and skips resource consumption when that piece's free-build key is active. `Player.PlacementCostDisabled` and `Player.NoCostCheat()` both read `m_noPlacementCost`. `Piece.FreeBuildKey()` chooses `NoCraftCost` for a piece with an `ItemDrop` or `Feast` component and `NoBuildCost` otherwise. These are possible explanations to check, not evidence that either mode was active during the user's test.

The public instance `Plant.UpdateHealth(double timeSincePlanted)` initially marks the plant healthy when the elapsed time is below ten seconds. After that it checks the terrain biome against `Plant.m_biome` and marks it unhealthy if they do not overlap; cultivated ground, roof, and space checks follow separately. On 2026-11-26 the user observed in vanilla, with the mod removed, that Barley and Flax can be placed outside the Plains, then turn brown with a wrong-biome tooltip.

### Build tooltip requirement amounts - 2026-11-26

Evidence: The game was updated on 2026-11-26. Targeted Mono.Cecil metadata and method-body inspection of `assembly_valheim.dll` MVID `0b95eb42-8fc0-4903-9058-dad694621afb`, SHA-256 `B885C68E7F4865BB398543D4A36246B68B547DED9A0FCB8D1CEFE5F762EA3BA0`. All storage mods' patch signatures were rechecked against this fingerprint with the signature validator. The other method-body claims above remain tied to their earlier fingerprints.

`Hud.SetupPieceInfo(Piece piece)` is private instance `void`. For each piece resource, it calls `InventoryGui.SetupRequirement` with `craft = piece.FreeBuildKey() == NoCraftCost`, so Cultivator plants that carry an `ItemDrop` pass `true` and ordinary Hammer pieces pass `false`. `SetupRequirement` writes only the **required** amount (`GetAmount(quality) * craftMultiplier`) to the `res_amount` `TMP_Text`. It uses the player's `Inventory.CountItems(name, -1, true)` only to flash the text red when the amount is insufficient, unless the matching no-cost global key is set.

[`PlacementPieceInfoPatch`](../../ValheimMods.Common/src/Placement/PlacementPieceInfoPatch.cs) opens a requirement scope around `SetupPieceInfo` for the local player and a registered tool. Insufficiency flashing therefore includes eligible storage. [`PlacementRequirementDisplayPatch`](../../ValheimMods.Common/src/Placement/PlacementRequirementDisplayPatch.cs) then shows `inventory:storage` in the vanilla required amount's place, raising that amount one line, through [`RequirementAmountText`](../../ValheimMods.Common/src/RequirementAmountText.cs). `res_amount`'s text, size and white/red flashing are never modified; only its position moves. The counts live in a sibling `hoose_res_counts` label, cloned once per reused requirement element with `Object.Instantiate(res_amount.gameObject, elementRoot)`. The clone has auto-sizing off, the source font size, `TextOverflowModes.Overflow`, `TextWrappingModes.NoWrap` and yellow (`#FFD700`) vertex colour. Tooltips and the crafting panel use a `hoose_res_counts_raised` label that keeps `res_amount`'s original position, while `res_amount` moves up one rect height whenever counts are shown and returns when they are cleared, because in game on 2026-11-26 a label below it was hidden under the control beneath the crafting panel's requirement row. (`Apply` can still place a `hoose_res_counts` label below an unmoved amount, but no patch uses that now.) In game on 2026-11-26, the raised amount in the build tooltip overlapped material names that wrap onto two lines (for example Black Metal), while crafting-panel names stayed on one line. So while counts are shown in a tooltip, the `res_name` `TMP_Text` (found by name in `SetupRequirement` IL) is set to `TextWrappingModes.NoWrap` with auto-sizing between its original size and half of it; its original wrapping, auto-sizing and font sizes are restored when counts are cleared. The crafting prefab's `res_name` settings were not inspected. A prefix clears it before every `SetupRequirement`, because elements are reused across tools and recipes. That is not enough on its own: in game on 2026-11-26, the slot after a two-material piece's resources (reused for the crafting station) kept stale counts, and so did surplus crafting-panel slots after choosing a recipe with fewer requirements. Those slots are drawn without `SetupRequirement`. So `PlacementPieceInfoPatch` clears every `Hud.m_requirementItems` entry (public `GameObject[]`), and `RequirementListClearPatch` prefixes private `InventoryGui.SetupRequirementList(int quality, Player player, bool allowedQuality, int amount)` to clear every `m_recipeRequirementList` entry (public `GameObject[]`) and restore raised amounts. In game on 2026-11-26, counts also persisted after switching to the Upgrade tab, or to another station, with nothing to upgrade: the 2026-11-26 IL of `UpdateRecipe` hides every slot with public static `InventoryGui.HideRequirement(Transform elementRoot)` and does not call `SetupRequirementList` then, so `RequirementHideClearPatch` prefixes `HideRequirement` to clear each hidden slot. Signatures were inspected in SHA-256 `B885C68E7F4865BB398543D4A36246B68B547DED9A0FCB8D1CEFE5F762EA3BA0`; method bodies were not. The text is `inventory:storage` with a side left blank when it is zero (`12:`, `:56`), and the label is empty when both are zero. It counts the same closed, owned, in-range containers used for placement. Other tools and remote players keep the vanilla required-only text and position. Stub tests cover the text, the vanilla-only text and insufficiency with no materials, the inaccessible-container exclusion, scope cleanup and the Hammer without BuildFromStorage. Live rendering, colour, text fit and controller layouts are not yet confirmed in game.

## Pitfalls

- Keep the storage count patch inside the `CanBuild` requirement scope. `HaveRequirements` is also used for material discovery and other build UI checks.
- Build availability and cost consumption are separate steps. Plan the full cost before placement to prevent duplicate requirements from allocating the same stack twice.
- Preserve the current-station/upgrader-resource filter and the free-build key. Do not globally inflate `Inventory.CountItems`.
- `Inventory.RemoveItem(string, int, int, bool)` returns `void`; validate planned storage counts before consuming and surface unexpected changes.
- Successful placement can still produce an unhealthy plant under vanilla growing rules; do not confuse unhealthy growth with a rejected placement or refund its normal cost.

## Unknowns

- The user checked the earlier single-player Hammer placement, UI, and save/reload scenarios; their report does not establish the later shared-engine behavior.
- Actual Cultivator prefab identity, every available menu entry, material discovery, terrain/biome/spacing, stamina/durability, controller input, and plant growth status require the [farming checklist](../../FarmFromStorage/TESTING.md).
- Multiplayer ownership changes, concurrent container access, and persistence after multiplayer save/reload need in-game validation.
- In game on 2026-11-26, appending a `\n` second line inside `res_amount` shrank the font and the second line was not visible. That matches a single-line, auto-sized field whose overflow clips, but the prefab's TMP settings and rect were not inspected. Appending on the same line was truncated for long counts. In game on 2026-11-26 the label below the build and Cultivator tooltip amount displayed correctly and the raised crafting layout looked correct; raising the tooltip amount overlapped two-line material names. Whether TMP auto-sizing shrinks a no-wrap `res_name` enough to fit, and how small it gets, is not yet confirmed in game; very large counts are unchecked.
- The current implementation does not request ownership of a chest it does not already own. Opening and closing it may make it eligible, but ownership can change and this is not guaranteed; see [Storage and ownership](Storage.md).
